## 질문 1

토큰 팩토리는 GPU를 늘려 답변을 빨리 생성하는 것일까?

## 답변 1

대화에서는 LLM 추론을 대량 서비스로 운영하는 전체 체계를 가리키는 표현으로 사용했다. 고정된 단일 소프트웨어 이름으로 보지 않는다.

목표는 답변 품질, 첫 응답 지연, 동시 처리량, GPU 가동률, 요청당 비용을 함께 관리하는 것이다. GPU가 많아도 요청 대기·메모리·통신·비효율적인 배칭이 병목이면 효과가 제한된다.

## 질문 2

vLLM을 도입하면 모델이 더 정확해질까?

## 답변 2

| 구성요소 | 주요 책임 |
| --- | --- |
| 모델 | 학습된 가중치로 답변 후보 계산 |
| vLLM | 모델 실행, 요청 스케줄링, 배칭, 캐시·메모리 관리 |
| 서비스 플랫폼 | 고객 인증, 모델 권한, 제한, 라우팅, 사용량, 배포·운영 |

vLLM의 주목적은 이미 학습된 모델을 효율적으로 실행하는 것이다. 모델의 지식과 답변 품질은 모델 선택·프롬프트·근거 제공·학습·평가도 함께 봐야 한다. [vLLM 공식 문서](https://docs.vllm.ai/en/latest/)

### GPU 증설 이외의 최적화

- Continuous batching: 끝난 요청의 자리에 새 요청을 넣어 처리 자원 활용
- KV cache: 앞선 토큰의 중간 계산을 재사용
- PagedAttention: KV cache를 블록 단위로 관리해 메모리 낭비 완화
- Prefix caching: 동일한 입력 접두사의 계산 재사용
- Quantization: 가중치 등의 표현 정밀도를 줄여 메모리·데이터 이동량 감소
- Speculative decoding: 후보 토큰을 먼저 제안하고 대상 모델이 검증

각 방법의 품질·지연·처리량 효과는 모델과 하드웨어, 요청 형태에 따라 실측해야 한다. [vLLM 내부 구조 설명](https://vllm-project.github.io/2025/09/05/anatomy-of-vllm.html)

## 질문 3

추론 엔진이 있는데 서비스 쪽에서 무엇을 더 구현해야 할까?

## 답변 3

아래는 대화에서 사용한 개념 구조이며 특정 회사의 운영 구성을 확인한 결과는 아니다.

~~~text
고객 앱
  → 인증·모델 권한·요청 한도
  → 모델·고객·서버 상태 기반 라우팅
  → vLLM 인스턴스 → GPU와 모델

별도 운영 흐름
요청 ID·시작·완료·취소·실패 → 고객별 사용량 기록
엔진 지표 → 모니터링·배포·장애 대응·용량 조정
~~~

스트리밍 도중 연결이 끊기면 뒤의 계산 취소와 실제 사용량 처리가 필요하다. 재시도 시 답변·정산이 이중 반영되지 않도록 요청 상태를 추적한다.

엔진의 처리 지표와 고객별 정산 원장은 목적이 다르다. /metrics의 집계 지표만으로 고객별 요금 기록이 완성되지는 않는다. [vLLM 운영 지표](https://docs.vllm.ai/en/latest/usage/metrics/)
