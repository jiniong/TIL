## 질문 1

ECS, EKS, EC2, Fargate는 서로 어떤 관계일까?

## 답변 1

컨테이너를 관리하는 체계와 실행 자원을 제공하는 방식을 나누어 본다.

| 기준 | 서비스 | 역할 |
| --- | --- | --- |
| 컨테이너 관리 | ECS | AWS의 방식으로 Task 배치·실행 상태 관리 |
| 컨테이너 관리 | EKS | 관리형 Kubernetes로 Pod와 관련 리소스 관리 |
| 실행 자원 | EC2 | VM을 빌리고 호스트의 용량·OS·운영을 관리하는 방식 |
| 실행 자원 | Fargate | 지원되는 Task·Pod의 요구 자원을 지정하면 AWS가 실행 인프라 관리 |
| 이미지 보관 | ECR | 컨테이너 이미지를 저장하는 레지스트리 |

ECR은 서버를 빌리는 서비스가 아니다. EC2와 Fargate를 ECS/EKS와 같은 축에 놓고 비교하면 역할이 섞인다. 위 표는 대화에서 다룬 기본 구분이며, 각 서비스의 전체 실행 옵션 목록은 아니다.

## 질문 2

EC2에 Docker로 API를 띄우는 것과 EKS에서 Pod로 띄우는 것은 무엇이 다를까?

## 답변 2

EC2에서 Docker를 직접 운영하면 컨테이너 실행·재시작·배포·서버 간 배치 등을 직접 구성해야 한다. EKS에서는 Kubernetes에 원하는 상태를 선언하고, 컨트롤러와 스케줄러가 그 상태를 유지하도록 동작한다.

EKS를 사용해도 애플리케이션 설정과 배포 전략, 리소스 요구량, 네트워크·권한 설계가 사라지지 않는다. Kubernetes 운영 복잡도와 필요한 기능을 함께 판단해야 한다.

## 질문 3

Fargate를 쓰면 서버와 관련된 설정은 전부 AWS가 해 줄까?

## 답변 3

| 사용자가 지정 | AWS가 관리하는 실행 인프라 |
| --- | --- |
| 컨테이너 이미지와 Java 등 런타임 구성 | 호스트 서버와 호스트 OS 운영 |
| CPU·메모리 요구량 | 실제 실행 자원 배치·할당 |
| 환경변수·네트워크·권한 | 인프라 유지보수 |

Java를 컨테이너 이미지에 준비하고 CPU·메모리를 얼마나 요청할지는 사용자의 책임이다. 물리 서버를 지정하지 않는다고 자원 요구량까지 생략할 수 있는 것은 아니다.
