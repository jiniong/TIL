## 목표와 최신 실습 범위

Windows PC에서 Ubuntu VM으로 온프레미스 Kubernetes 설치와 인터넷이 차단된 환경의 이미지 반입을 연습하려는 실습이다.

처음에는 control·worker VM 두 대를 계획했다. 10월 29일 대화에서 호스트 메모리 여유를 확인한 뒤, 사용자가 VM 한 대로 진행하도록 변경했다. 두 노드 실습을 완료한 기록이 아니다.

## 당시 확인한 환경

| 항목 | 대화에서 확인된 값 |
| --- | --- |
| Ubuntu | 26.04.1 LTS |
| VM 호스트 이름 | k8s-control-1 |
| VM 자원 | 메모리 3GB, CPU 2개 |
| Windows 전체 RAM | 약 15.73GB |
| Windows 당시 가용 RAM | 약 1.7~2.2GB |
| 준비 상태 | Ubuntu 설치와 로그인 확인 |

이 값은 당시 관측치이며 현재 PC 상태를 다시 측정한 결과가 아니다. 두 번째 VM에도 3GB를 할당하면 여유량을 넘길 수 있어 단일 VM으로 범위를 줄였다.

## 네트워크 구성 원리

- NAT: 준비 단계에서 설치 파일·이미지 등을 인터넷으로 받는 통로
- Host-only: Windows와 VM 사이의 통신을 유지하는 통로
- 오프라인 실습: 인터넷 통로인 NAT를 끊고, 필요한 로컬 통신만 유지

두 어댑터를 모두 끊으면 Windows에서 VM에 접근하는 통로도 사라질 수 있다. Host-only가 있다고 인터넷이 자동 차단되는 것도 아니므로 다른 어댑터·라우팅을 확인해야 한다.

## 설치 과정에서 겪은 문제

### 회색 네트워크 설정

실행 중·저장됨 상태에서는 변경할 수 없는 VM 설정이 있다. 게스트 정상 종료 후 관리자 화면에서 전원 꺼짐 상태인지 확인하고 설정을 연다. 일시정지나 상태 저장을 완전 종료와 혼동하지 않는다.

한국어 화면의 케이블 연결됨 항목을 기준으로 안내를 맞췄다. 화면 구성은 VirtualBox 버전과 고급 설정 표시 여부에 따라 확인해야 한다.

### 설치 로그와 완료 메시지 혼동

Try or Install Ubuntu Server 진입 후 로그가 보인다고 설치가 끝난 것은 아니다. 설치 진행 로그와 실제 부팅 완료·로그인 가능 상태를 구분했다.

~~~bash
sudo tail -n 30 /var/log/installer/curtin-install.log
cat /etc/os-release
free -h
ip -br address
ip route
~~~

위 명령은 로그·버전·메모리·주소·경로 확인용이다. 대화에서 soft lockup 경고도 관찰했지만, 한 줄만으로 설치 실패를 단정하지 않고 후속 로그와 부팅 상태를 확인했다. 최종적으로 Ubuntu 설치와 로그인은 확인됐다.

## K3s 오프라인 설치 준비 계획

K3s는 단일 노드에서 관리와 워크로드 실행을 함께 연습할 수 있다. 실제 설치 시에는 선택한 릴리스·CPU 아키텍처가 일치하는 바이너리와 air-gap 이미지 묶음을 준비해야 한다. 이미지 수동 반입 경로와 설치 환경변수는 [K3s 공식 에어갭 문서](https://docs.k3s.io/installation/airgap)를 기준으로 확인한다.

- K3s 바이너리·설치 스크립트·동일 릴리스의 이미지 묶음 준비
- 테스트용 Nginx 이미지도 외부 pull 없이 사용할 수 있도록 별도 준비
- 파일 반입 후 인터넷 통로 차단 여부 확인
- K3s 설치 후 Node 상태·시스템 Pod 상태 확인
- 앱 배포 후 이미지가 인터넷 없이 준비되는지와 접속 확인
- Pod 재생성 후에도 같은 조건에서 다시 실행되는지 확인

위 목록은 초기 실습 계획이다. 10월 30일 확인한 후속 결과는 아래에 구분해 기록한다. 단일 노드에서는 노드 장애를 견디는 고가용성을 검증할 수 없다.

## 후속 실습과 병원 폐쇄망 적용

### 관찰한 후속 결과

사용자는 호스트 전용 주소를 고정하고 기본 경로가 표시된다고 보고했다. Kubernetes API는 Deployment의 잘못된 selector·template 구조와 Service의 잘못된 NodePort에 검증 오류를 반환했다. 이는 API가 응답했다는 증거이며 Node Ready나 앱 접속 성공의 증거는 아니다. NodePort의 자릿수 오류 수정안을 안내했다. 재부팅 후 networkd-wait-online 대기가 다시 보고됐으며 복구는 아직 확인하지 못했다.

### 질문: 실습이 실제 병원망 설치와 어떻게 연결되는가

아래는 특정 병원의 정책이 아닌 설명용 설치 시나리오다. 실제 반입 경로·보안 검토·접속 허용은 해당 병원 담당자와 정한다.

1. 병원 서버·OS·CPU 아키텍처·자원과 기존 Kubernetes 유무를 먼저 확인한다. 기존 클러스터가 있으면 앱 배포가 중심이며 K3s를 별도로 설치하지 않는다. Kubernetes 자체가 필수인 것도 아니다.
2. 외부 준비 환경에서 앱을 빌드하고 OS 의존성, 실행 이미지, 설치 스크립트, 배포 YAML 또는 Helm chart를 버전에 맞춰 묶는다. 필요한 제품이면 모델 가중치·오프라인 라이선스도 포함한다.
3. 병원이 승인한 반입 절차로 파일을 전달하고 무결성과 필요한 검사를 수행한다. 서버의 인터넷을 잠시 켜서 다운로드하는 것을 기본 절차로 가정하지 않는다.
4. 새 클러스터가 필요한 경우 준비한 파일로 설치한다. 이미지는 각 노드에 직접 반입하거나 내부 레지스트리에 저장할 수 있다. [공식 K3s 오프라인 설치](https://docs.k3s.io/installation/airgap)
5. 병원용 주소·저장소·설정·인증정보를 별도 적용하고 배포한다. 실습의 Nginx 대신 실제 프런트·백엔드·추론 서버 등이 올라간다. 내부 DB 연동과 사용자 접속 경로는 따로 구성한다.
6. 외부 접속 없이 앱·데이터 연동·재생성·재부팅 복구를 검사한다. 업데이트도 새 버전의 반입과 배포이며 이전 버전으로 되돌릴 수 있어야 한다.

K3s 설치는 앱을 실행할 Kubernetes 기반을 준비하는 일이고, kubectl apply는 그 기반에 원하는 앱 상태를 전달하는 일이다. NodePort는 실습용 접속 경로이며 실제 병원의 내부 DNS·TLS·Ingress·로드밸런서 구성과 동일하다고 간주하지 않는다. 폐쇄망에서도 내부 네트워크 통신은 가능하며 인터넷 차단과 네트워크 전체 단절은 다르다.
